# FreeImage upstream patch archive

Checked **2026-11-05** against the [live SourceForge tracker](https://sourceforge.net/p/freeimage/patches/) and all 197 ticket records returned by its [REST API](https://sourceforge.net/rest/p/freeimage/patches?limit=100&page=0). Candidate exports use committed history at that baseline; uncommitted working-tree changes are excluded.

The archive contains **29 original attachments on 29 tickets**: historical #115 and #170–197. Two further tickets from `danoli3`, #96 and #198, link to code without attachments. #169 is an empty duplicate of #170. Tickets #170–173 are anonymous, included because the recorded fork submission series maps them to our commits. Other contributors' patches are outside the attachment archive.

SVN trunk still reports **r1911**, last changed 2024-04-18 (`svn info https://svn.code.sf.net/p/freeimage/svn/FreeImage/trunk`, checked 2026-11-05). Tracker status and submission do not establish source acceptance. #96 is closed, #115 is open, and #170–198 have an empty API status field; no individual SVN acceptance revision has been established here.

## Application and replacements

- #169 is an accidental empty ICO stub; use #170.
- Apply #179 before later Exif changes, #180 before #181, and #178 before #181's TIFF changes.
- Vendor sequence for SVN r1911: **#182 → #190 → #191 → #192 → #193 → #194 → #195 → #196 → #197**. Shared build/project files make the order significant. **#197 replaces #183; do not apply both.**
- Submitted SVN patches use root-relative paths (`-p0`). For vendor gzip patches, decompress into a temporary file and use `patch --dry-run -E -p0`, then `patch -E -p0` from the target tree root. `-E` removes obsolete files. ZIP bundles contain their own patch and notes. The historical #115 patch targets FreeImage 3.17.0; inspect its headers and original instructions separately.
- `sourceforge/96/linked-commits` and `sourceforge/198/linked-commits` contain locally exported Git diffs (`-p1`) of commits linked in those tickets. These are **not SourceForge attachments**. #198's RAS fix is already part of #180; its IFF fixes have ticket links but no uploaded patch.
- Earlier [loader regression notes](2026-10-13/README.md) and [vendor-series validation](2026-10-13-vendors/README.md) are retained. They describe the original preparation work and its limits, not new validation performed for this archive.

**#190 formatting:** the decompressed uploaded patch ends with an unterminated context line. `git apply --numstat` rejects it as corrupt at line 202. The original gzip is preserved byte-for-byte; [this separate parsing companion](sourceforge/190/openjpeg-2.5.4-project-with-final-newline.patch) appends exactly one LF byte and passes strict patch parsing. This is a local derivative, not an uploaded replacement or a new SVN application test.

The downloaded vendor patches already contain several fixes previously listed as needing submission checks: #193 includes the WebP ARM64EC guards in `src/dsp/cpu.h`; #197 includes the libdeflate ARM64EC detection in `common_defs.h`, strict-C11 Linux feature declarations in `lib/arm/cpu_features.c`, and Android pre-28 aligned allocation in OpenEXR's `internal_zstd.c`. These do not need separate duplicate submissions. [Fork reference exports](sourceforge/197/fork-references) are retained for provenance (the WebP part belongs to #193).

## Maintaining the archive

Use the ticket number as the stable submitted-artifact directory. Preserve downloaded bytes and compressed formats; add an attachment URL, size and hash to the manifest. Record a new ticket only after submission, and an SVN revision only after verifying application. Candidate patch exports must always identify the exact fork commit and parent, plus whether they are adapted and validated for SVN.

No tickets, comments, attachments or other remote changes were posted while creating this archive. [Archive validation](archive-validation.json) covers hashes, gzip/ZIP integrity, patch parsing (with the documented #190 formatting exception), exact equality with the recorded Git diffs and local Markdown links. It does not repeat sanitizer builds or prove SVN application.
